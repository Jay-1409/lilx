02 / Execution

Five stages, one bounded request

The service presently makes one model call to plan and one to compose. Backend calls can run in parallel.

01 DISCOVERRead catalogGET /v1/operations returns approved GET operations, descriptions, and inline path/query parameters.
02 VALIDATECheck inputPOST /v1/requests requires nonempty text and an object JSON Schema under the size limit.
03 SELECTPlan + enforceGemma proposes up to ten calls. Server code rejects IDs outside the approved catalog.
04 CALL + COLLECTFetch JSONWorkers execute documented GETs, collect status and JSON, and fail the run on an upstream error.
05 RETURNCompose + checkGemma writes a candidate object. JSON Schema validation gates data; call status goes in trace.
03 / Boundaries

What the application enforces

These are code level boundaries, not promises made only in prompts.

Operations and credentials

The operator sets one backend base URL, one OpenAPI URL, and an operation allowlist at startup. The prompt cannot replace them. Backend and Google credentials are server side.

  • OpenAPI 3.x GET operations only; path and query parameters must be documented.
  • Caller bearer authentication is optional through LILX_API_KEY.
  • HTTP redirects are disabled for backend and model clients.

Limits and outcomes

A request is bounded by input size, ten planned calls, worker capacity, backend response size, and request/model timeouts.

  • Backend responses over 1 MiB and model responses over 128 KiB fail.
  • No approved call, upstream failure, or invalid composed JSON produces an error.
  • The final schema check verifies shape and types; it does not prove every statement is grounded.
Data exposure to resolveCurrent per-request JSONL logs include raw client, model, and backend bodies. Header credentials and credential-like URL query values are omitted or redacted, and file permissions are restricted, but the bodies can still contain sensitive data. This differs from the product guidance for a redacted operational trace.

06 / Decisions to make

Three choices that shape the next architecture

These should be settled before broadening connectors or promising field level provenance.

DECISION 01

Define response_format

Choose example template or JSON Schema, then specify required fields, nullability, nesting, and partial results.

Current code has chosen JSON Schema for execution. The product contract has not ratified it.
DECISION 02

Define connector scope

Decide how workspaces register APIs and how a caller narrows the approved set for one request.

Current configuration loads one backend spec at service startup.
DECISION 03

Define safe trace + evidence

Choose how each returned field cites a source, how gaps are shown, and what raw data must stay out of logs.

The existing response trace is operation level only; file logs contain raw bodies.
